<summary><b>Rodando o strapi</b></summary>

Pra começar, execute os comandos a seguir, para acessar o projeto, atualizar-lo, remover a node\_modules, instalar as dependências e rodar o projeto.

```dart
cd soma-bus-strapi 
git pull 
rm -rf node_modules
npm install
npm run develop
```

Quando rodar um link ficará disponível para acessar o painel de admin do strapi:<br />”To access the server ⚡️, go to: [http://localhost:1337](http://localhost:1337/)”.

<details>
<summary><b>Ambientes do strapi</b></summary>

O strapi tem três ambientes,:<br />- local: onde criamos e editamos componentes e coleções;<br />- homologação: cada marca tem seu strapi de homologação onde podem cadastrar os componentes para teste, e este ambiente também é usado para testes de desenvolvimento e QA.<br />- produção: ambiente que deve ser alterado apenas pela marca.

As novas branches devem sempre sair da branch de <b>homolog.</b><br /><br />\* Caso não tenha acesso ao strapi de homologação/produção, solicite acesso a equipe de desenvolvimento.<br /><br />No código, a alteração do ambiente acessado acontece no arquivo <i>marca</i>\_config, na propriedade de CMS cofig. (para o legado)<br />Na nova arquitetura, a atribuição do ambinete do strapi é no app\_module(da marca), e redefinir as variaveis de:<br /><b>cmsStagingToken</b>:<br /><b>cmsStagingUrl</b>:<br /><br />Para rodar localmente é necessária a definição do token, e sua atribuição.

</details>

<summary><b>Criação de novos componentes</b></summary>

A criação de um novo componente só acontece rodando o strapi localmente, em modo de homologação não é possível criar ou alterar componentes

<details>
<summary><b>Criando componentes no Strapi</b> <b>Content-Manager</b> é o lugar em que o conteúdo é criado, onde se atribui os valores de cada campo. <b>Content-Type Builder</b> é a área de criação das collections e componentes.</summary>

<br />Em Content-Type builder, crie um novo componente e selecione a category (é o nome da “pasta onde ele ficará dentro na seção de componentes (talvez seja preciso criar a categoria). Selecione um ícone apropriado, e continue.

![Figura 4](/img/geral/configuracoes-internas-strapi/img-04.webp)

<br />Crie cada um dos ítens que irá compor este componente (como Text para título, ou booleanos para ativo/inativo). O tipo de cor está disponível em “custom”.<br />Como nome dos items, use o padrão inglês e minúsculo. Coloque como “name” o valor correspondente em “api\_key” do prismic.<br />Acesse as “advanced settings” e configure seu item. Por fim, salve o novo componente.

![Figura 5](/img/geral/configuracoes-internas-strapi/img-05.webp)

<br />Acesse o content manager, selecione a collection onde seu componente deve aparecer, clique em “Create new entry”, depois defina a marca onde esse conteúdo será adicionado e clique em “Add a component to componente”. Adicione seu componente.<br />Salve e publique.<br />Ele deve passar a aparecer no seu projeto (no código).

:::info

Não esqueça de alterar a documentação do notion, se necessário.

:::

<details>
<summary><b>Cuidados ao criar componentes</b></summary>

<b>Não crie</b> atributos da collection <b>com o mesmo nome</b> de componentes, ou das propriedades dos componentes. (Isso mesmo, ajuda o Strapi a não se confundir, sério). Também não crie componentes na collection (atributos) repetíveis.

<b>Não aninhe componentes repetíveis.</b><br />Por exemplo: um componente card, usa um componente já existente, de forma repetível (imagine que é para cadastrar uma lista de filtros, de strings).<br />Não crie um componente carousel, que usa o componente já existente card, de forma repetível, pois isto se configura como aninhamento de componentes repetíveis, e o front-end do react não suporta.

<b>Cuidado ao forçar a criação de um componente</b><br />É possível criar o componente via strapi, e editá-lo no json, adicionando novos campos, alterando o nome das propriedades, etc.<br />Via interface do Strapi, não é possível aninhar componentes complexos, que tenham um de seus campos um componente já pré-existente. Pelo JSON é possível, mas tenha cuidado pois, na versão utilizada do Strapi, o backend suporta tal modificação, mas o front-end não. Isso pode gerar erros em homolog/produção, em que ao tentar acessar uma collection, via painel de admin, ela quebre.

<summary><b>Criando os componentes no código</b></summary>

Após criar o seu componente no strapi, é necessário alterar o nome do componente, pois o banco de dados só aceita identificadores (de tabelas, campos, índices, etc) com até 64 caracteres.  A solução adotada foi alterar o nome das tabelas de componentes. O Strapi gera por padrão "components\_\$\{nome\_da\_pasta\}\_\$\{nome\_do\_componente\}s", o padrão foi alterado para "c\_\$\{nome\_do\_componente\}s".

Quando você criar um componente novo, lembre de alterar o collectionName no arquivo JSON do componente:

![Figura 6](/img/geral/configuracoes-internas-strapi/img-06.webp)

&lt;image />

Acesse: <i>soma\_ui/lib/cms/models/components</i>

Crie um novo arquivo para o model do seu componente. O nome do arquivo deve ser padronizado “<i>nome\_componente\_cms\_component”</i>, e crie a classe como nomeComponenteCmsComponent, extendendo de CmsComponent.

Exporte o seu arquivo no arquivo components.dart.

Acesse: <i>soma\_ui/lib/cms/widgets/components</i>

Crie um arquivo para seu novo componente, que deve retornar o widget a ser renderizados (pode ser um preexistente).<i><br /></i>

Acesse:  <i>soma\_ui/lib/cms/sm\_cms\_component\_renderer.dart</i>

Acesse o arquivo cms\_componente.dart, e nele adicione o seu componente no switch. Como chave, utilize o componenteType (“\_\_component”).

WIDGET > sm\_cms\_component\_renderer.dart

e adicione o seu componente na lista.

<summary><b>Exportação/importação das configurações</b></summary>

As informações definidas em “configure de view” ficam salvas como configurações no banco de dados, e não são incluídas no Git pelo Strapi. Pra resolver foi adicionado um plugin de exportação/importação de configurações. A exportação é feita automaticamente quando você faz um commit, já a importação é feita manualmente pela tela "Config Sync Interface" nas "Settings" do painel:<br />

![Figura 11](/img/geral/configuracoes-internas-strapi/img-11.webp)

No  Strapi, “acesse Settings > Config sync \| Interface" e você verá as alterações pendentes, tanto coisas que você mudou e precisam ser exportadas, quanto coisas que outras pessoas mudaram e foram exportadas. Para que acessemos as configurações que foram definidas em outras máquina/outras pessoas, em nossa maquina é preciso importa-las.<br />Acesse via strapi, selecione as configurações, e clique em “import”.

No projeto, as configurações ficam salvas no soma-bus-strapi/config/sync. E são exportadas apenas quando você executa "git commit", e não são exportadas automaticamente depois de alterar.

Também é importante prestar atenção pra não importarem algo que delete o que vocês fizeram, igual merge de github. Esse plugin até tem uma telinha parecida quando você clica na tag de State para ver quais são as alterações:<br />

<summary><b>Espaçamento entre os componentes</b></summary>

Foi criado o SMCmsContentSpacer para adicionar o espaçamento entre os componentes, ele deve ser colocado dentro de cada um dos componentes de CMS que precisarem ter espaçamento:

&lt;image />

O espaçamento é padrão 40 para todos os componentes e marcas, e é adicionado acima do componente.

Caso o componente não deva ter espaçamento baseado em alguma condição, pode ser usado o shouldHaveSpacing para especificar essa condição:

&lt;image />

Como é comum que os componentes não tenham espaçamento quando vieram após determinado componente (CouponBanner não tem espaçamento se estiver após o CarouselList, por exemplo), já existe o construtor noSpacingWhenPreviousComponentIs especifico implementando essa condição. Nele você passa o tipo do model do componente que não deve ter espaçamento:

&lt;image />

## Ponto de atenção

Como antes lidávamos com o espaçamento abaixo do componente (vide as propriedades hasBottomSpacing que temos em vários componentes) e agora o espaçamento é acima do componente, talvez tenhamos que adaptar o cadastro de alguns componentes para essa nova forma de pensar. Caso essa nova forma seja muito problemática, acredito que teríamos que voltar a pensar no espaçamento abaixo do componente.

## Motivação

Com esse SMCmsContentSpacer temos duas coisas diferentes do modelo anterior: espaçamento acima ao invés de abaixo e espaçamento dentro dos componentes (dentro do build) ao invés de entre os componentes. Vou explicar um pouco dos motivos disso.

O espaçamento acima me pareceu fazer mas sentido pela forma de pensar sobre componentes que não tem espaçamento em certos casos. Me pareceu mais natural pensar que "O CouponBanner não tem espaçamento quando está depois do CarouselList" do que "O CarouselList não tem espaçamento quando está antes do CouponBanner".

Já sobre o espaçamento estar dentro do build dos componentes, é por conta de flexibilidade em cenários mais específicos. Por exemplo, o SpotProductClock não deve aparecer caso o tempo do reloginho tenha terminado, e o seu espaçamento também não deveria aparecer. Para fazer essa lógica, é necessário ter acesso ao estado do componente, algo que só é possível fazer dentro dele.

<summary><b>MaxDiscountConfig</b></summary>

Esta configuração refere-se ao desconto máximo que um produto pode ter. Este valor foi pré-definido no código como 80%. E será sobrescrito pelo conteúdo definido neste arquivo de configurações remotas.

<b>max\_discount</b>: o desconto maximo que pode ser aplicado.

<b>Exemplo de preenchimento</b><br />80

<b>allowed\_domains</b>: lista de dominios permitidos pra comprar com desconto acima do limite. Verifica se o email do usuário contém o domínio especificado.<br />Ou seja, podemos adicionar nesta lista “farm.com.br” e "somagrupo.com.br", e caso o email do usuario contenha este texto, o produto não será removido da <br />sacola dele (Mesmo que exceda o limite de desconto).

<b>Exemplo de preenchimento:</b>

[somagrupo.com.br](mailto:diego.assim@somagrupo.com.br)

<b>forbidden\_sku\_ids</b>: lista de skuid que estão proibidos. Caso tenha algum problema <br />específico com um produto, pode-se adicionar seu PRODUCTID, e caso ele <br />esteja na sacola do usuario, será removido.

<b>Exemplo de preenchimento:</b>

12345
