01 · Processos · App Plataforma × App Custom

Como vamos trabalhar

Guia operacional: ownership das libs, versionamento por tag, automação de release e autonomia das marcas — sem acoplar lib ao ciclo do app.

App Plataforma App Custom Release automação 1 branch + tags Marcas opt-in Release branch Feature flag

Em 30 segundos

  1. Lib tem dono: ele aprova o PR; a automação gera tag + changelog.
  2. Feature grande? Antes: call de refinamento e 1 task por lib.
  3. Lib versiona por tag (não por branch develop/homolog).
  4. Marca escolhe quando atualizar a lib.
  5. Custom pode mexer em lib — mas sempre com o dono.
  6. Toda feature nasce com feature flag; sem flag na homolog → revert.

02 · Arquitetura do app

Como o ecossistema se organiza

Apps de marca (Farm, Hering, Reserva…) consomem libs compartilhadas. App Plataforma evolui as libs; App Custom entrega no app da marca.

De cima para baixo: app da marca → commons → libs de plataforma

Camadas dentro de uma feature

Camada de apresentação (UI)

Fluxo típico no design system — feature cross-brand

Template → composition_components → core_components → Tokens

Camada lógica (dados)

Fluxo típico no core / commons

Cubit → UseCase → Repository → Model
Feature nova de plataforma pode tocar várias libs (core, ui, commons, cms…). Por isso o refinamento quebra em 1 task por lib — cada uma com owner e versão própria.

04 · Papéis

Quem faz o quê

Fronteira explícita: App Plataforma × App Custom.

App Plataforma

Cuida das libs

  • Refina e quebra o trabalho por lib
  • Desenvolve e testa nas libs
  • Dono aprova o PR; automação publica a versão
App Custom

Cuida das marcas

  • Entrega no app da marca
  • Decide se atualiza a lib
  • Se precisar mexer na lib, alinha com o dono

05 · Feature de plataforma

Quando chega uma feature

Cinco passos, nesta ordem.

1

Call de refinamento técnico

O time define o que vai em cada lib (ui, core, commons…).

Quem: App Plataforma + donos das libs
2

Uma task por lib

Cada lib afetada ganha um card no Jira. Sem card = não começa.

Quem: dono / App Plataforma
3

Desenvolver e testar

Código + testes da lib. Abrir PR com commit padronizado.

Quem: quem pegou a task
4

Dono aprova o PR

Sem aprovação, não tem merge — e sem merge, a automação não roda.

Quem: dono da lib
5

Automação gera a versão

Action cria tag, changelog (do card Jira), move o card e avisa no Teams.

Quem: GitHub Action
Importante: subir versão da lib não sobe versão da marca. A marca atualiza depois, se quiser.

08 · Release da marca

Uma branch + release temporária

Só main + release/X.Y.Z temporária. Toda feature nasce com feature flag: se reprovar na homolog, desliga no remote; sem flag, faz revert.

Azul = main · âmbar = release · teal = flag remota · coral = revert

Antes

develop → homolog → main

  • Três linhas longas para sincronizar
  • 1 task ruim trava o lote inteiro
  • Homolog = tip de develop
Depois

main → release → flag / tag

  • Feature nasce com feature flag
  • Reprovou → desliga no remote
  • Sem flag → revert na release
Feature flag Obrigatória em toda feature nova. Preferencial para tirar do pacote na homolog.
main Única branch longa. Features entram via PR.
release/X.Y.Z Temporária: homolog + loja. Revert só se não houver flag. Apaga depois da tag.
Tag vX.Y.Z O que foi à loja — imutável. Changelog / GitHub Release junto.

Ciclo completo

1

PR para main com feature flag

Card → feat/iddocard. A feature já nasce atrás de uma flag remota.

2

Cortar a release

Lote fechado → criar release/2.0.0 a partir de main.

3

Homolog — se reprovou

1º desligar a flag no remote (sem rebuild). 2º se não tiver flag → revert só na release.

4

Subir para a loja

Publicar a partir do pacote da release (flags desligadas ou reverts aplicados).

5

Tag + changelog

Tag v2.0.0 no commit que foi à loja + GitHub Release.

6

Apagar a release/2.0.0

main continua; a versão fica na tag. Flag pode ser religada depois, na próxima versão.

Quem: App Custom / release
Ordem de eject: feature flag remota → se não existir, revert na release/*. Nunca reverter em main só para salvar a homolog. Se houve revert na release, não mergear a release de volta em main.

09 · Git

Git e padrões (o básico)

Menos branches, mais clareza no artefato que a marca consome.

Branches (marca) Só main + release/X.Y.Z temporária. Sem develop/homolog longas.
Branches nas libs Uma branch principal (ex.: main). Sem depender de develop/homolog.
O que a marca usa A tag da versão (v1.4.2), nunca a ponta da branch.
Commits Padrão Conventional Commits + skill de commit para o time.
Changelog Texto claro, preferencialmente puxado da descrição do card.

12 · Atenção

Pontos de atenção

Obrigatórios para o fluxo funcionar de ponta a ponta.

1

Codemagic: parar de clonar as libs

Hoje o script do Codemagic clona os projetos das libs ao lado do app. Com consumo por tag, o build da marca resolve as libs via git + ref no pubspec, sem clone manual dos repositórios irmãos.

2

Toda PR nas libs vira tag — sem exceção

Para changelog, Jira, Teams e marcas opt-in funcionarem, toda PR mergeada nas libs deve gerar uma tag de versão. Sem tag, a marca não tem artefato fixo para consumir.

3

Homolog da marca builda de release/*

Não buildar homolog do tip de main durante o ciclo da versão. Sem branch de release temporária, o lote fica preso. Depois da loja: tag + changelog e apagar a release.

4

Feature flag obrigatória · revert é fallback

Toda feature nova nasce com feature flag. Se reprovar na homolog: desligar no remote. Só se não houver flag → revert na release/*.
